# SeniorAI — pinned dependencies
#
# Pinned to the exact combination running in production on the Kolkata NUC
# as of 2026-05-25 (the rebuild that recovered from the pygame entry_points.txt
# corruption). Top-level AND transitive deps are pinned so that a fresh
# `pip install -r requirements.txt` reproduces today's working state byte for
# byte — important because the NUC has no observability and "rebuild the
# venv after a power cut" is a recovery procedure we've already had to run
# once.
#
# To intentionally upgrade something:
#   1. On a dev box: bump the pin, run `pip install -r requirements.txt --upgrade`
#   2. Test all three buttons (chat / vision / telegram-send) + restart loop
#   3. Re-freeze the transitives:  pip freeze | sort
#   4. Update both the changed top-level pin AND any transitive pins it
#      pulled along with it. Commit the full diff.
#
# Do NOT loosen a pin to `>=` without going through that flow — the last time
# google-genai's transitives drifted, we got pydantic 2.13.3 instead of
# 2.13.4, which is harmless, but a major version drift (e.g. google-genai
# 2.x -> 3.x) would silently break the app on the next rebuild.
# =============================================================================

# pynput is our Windows-dev keyboard backend. On Linux we use evdev directly
# (INPUT_BACKEND=evdev) so pynput is never imported. Skipping it on Linux also
# avoids pynput's transitive dep on the evdev SOURCE package, which would try
# to compile against kernel headers — see evdev-binary line below.
pynput==1.8.1 ; sys_platform != "linux"

# evdev is Linux-only. Use evdev-binary (prebuilt wheel from the same upstream)
# so we don't need kernel headers to compile the C extension at install time.
# The Python import is still "import evdev" — evdev-binary installs the same
# package, just from a binary distribution.
evdev-binary==1.9.3 ; sys_platform == "linux"
